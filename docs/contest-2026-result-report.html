02 / PROBLEM & EXPERIENCE

바이브코더의 속도는 지키고,출하 기준은 흐리지 않는다

사용자는 규칙 목록을 해석하러 온 것이 아니다. 지금 출하할 수 있는지, 무엇부터 고쳐야 하는지, 아직 무엇을 보지 못했는지를 알고 싶다.

해결하려는 네 가지 공백

  1. 사이트: 디버그 노출, 잘못된 헤더와 캐시, 민감 응답이 배포본에 남는다.
  2. API: 인증과 인가 경계가 빠지거나 사용자 간 데이터 접근이 섞인다.
  3. 데이터: 한국 개인정보가 과수집되고 보유·파기·로그 경계가 구현에서 누락된다.
  4. 운영: secret, dependency, suppression, CI와 출하 증거가 서로 분리된다.

사이트

배포 산출물, 공개 노출, 헤더, 캐시, 디버그 신호와 권한 있는 제한적 probe를 확인한다.

API

route, auth boundary, IDOR, 관리자 경계와 서버·클라이언트 신뢰 경계를 추적한다.

데이터

개인정보 필드, 흐름, SQL AST, RBAC·RLS, 저장, 로그, 보유와 파기를 검수한다.

운영

secret, dependency, MCP policy, CI, suppression, SBOM과 출하 근거를 연결한다.

SHIP

네 영역이 모두 실행되고, blocking finding이 없으며, 요구된 출하 증거와 권한 assertion이 충족될 때만 판정한다.

HOLD

위험, 읽지 못한 파일, 한도 초과, source drift, 제어 오류, 생략 영역, 만료된 suppression 중 하나라도 남으면 통과시키지 않는다.

깊게 보는 방식

  • 운영 source와 설정, 한국 데이터 필드, route와 데이터 흐름을 우선순위로 탐색한다.
  • 테스트, 문서, 생성 리포트와 대규모 샘플은 장기 review와 Guardian에서 이어 본다.
  • 빠른 범위가 파일 수나 크기 한도를 넘으면 범위 미완료 finding으로 올린다.
  • 검사 중 파일이 바뀌거나 symlink·junction 경계를 만나면 source drift와 scope 위험을 기록한다.

증거를 남기는 방식

  • 민감 원문 대신 keyed fingerprint, detector subtype, body·header 위치와 response hash를 남긴다.
  • passive 후보 신호와 권한 있는 deep 검증을 서로 다른 주장으로 표시한다.
  • control error도 Guardian-shaped HOLD envelope로 통일한다.
  • suppression은 소유자, 이유, 만료, scope hash가 결속된 경우에만 인정한다.
K-Guard MCP는 앱의 사업 의도나 법률상 적법성을 인간처럼 확정하지 않는다. 코드와 설정에서 확인 가능한 구현 신호, 검수 범위, 출하 증거를 보수적으로 판단한다.

07 / DEVELOPMENT STORY

검수 절차와 기록을제품의 중심으로

대표 제출자 이풍현은 40세 공무원이다. 이 배경은 화려한 탐지 숫자보다 누가, 어떤 범위를, 어떤 근거로 확인했는지를 남기는 제품 관점으로 이어졌다.

개발 관점

바이브코딩은 비전공자도 아이디어를 실제 서비스로 옮길 수 있게 했다. 반면 출하 직전 검수는 전문 용어와 여러 도구 사이에 흩어져 있다. K-Guard MCP는 그 간극을 “옆자리 시니어에게 맡긴다”는 익숙한 경험으로 바꾼다.

모르는 것을 탓하지 않는다. 다만 출하 기준은 흐리지 않는다.

공무원이라는 제출자 배경은 기능 구현뿐 아니라 검토 절차, 책임 경계, 근거 기록을 제품 설계의 핵심으로 삼는 관점으로 연결됐다. 특정 기관의 업무나 데이터를 사용했다는 의미는 아니다.

Principles

끝까지 잠근 다섯 약속

  1. 동적 확인은 사용자가 허가한 범위에서만 시행한다.
  2. 보지 못한 범위는 문제가 없는 범위로 바꾸지 않는다.
  3. 출하 권한은 Guardian high 한 곳에만 둔다.
  4. 민감 원문은 결과와 증거에 되돌려주지 않는다.
  5. 합성 성능과 실제 앱 성능을 같은 숫자로 말하지 않는다.

개발 강화 과정

1단계 · 흩어진 검사기를 하나의 Guardian으로 통합

scan, security gate, runtime 관찰, release qualification의 역할을 정리하고 최종 출하 권한을 canonical tool로 고정했다.

2단계 · 끈질긴 전체 리뷰와 fail-closed 범위 계약

작업 큐, continuation, 파일 한도, source drift, symlink·junction, 생략 영역을 terminal 판정과 연결했다.

3단계 · JS·TS framework와 DB 분석 깊이 강화

Next.js, Express, Supabase, Firebase, SQL AST, RBAC·RLS와 cross-file 흐름 규칙을 확장했다.

4단계 · MCP runtime과 에이전트 권한 경계 강화

stdio 양방향 interceptor, Streamable HTTP 검증, identity, JIT·JEA, policy decision과 감사 로그를 추가했다.

5단계 · 실증과 공급망 근거를 제품 게이트로 승격

공개 benchmark, 다국어 검증팩, SBOM, 라이선스 closure, 재현 빌드, provenance와 field campaign 계약을 자동화했다.

아직 인간 시니어와 동급이라고 단정하지 않는다. 완전한 inter-procedural 의미 이해, 앱의 사업 의도, 법률 판단, 모든 취약점 탐지는 제품 경계 밖이며, 실제 앱 정확도는 외부 라벨이 채워진 범위만 공개한다.

Planned field protocol
